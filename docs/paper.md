# uni-mem：面向异构编码智能体的网关式统一记忆层

## 摘要

主流编码智能体（coding harness），如 Claude Code、Codex CLI，各自带有长期记忆机制，但这些记忆格式不同、存储分离、彼此不可见，形成一个个"记忆孤岛"。基于 MCP 或 hook 的记忆方案虽然可以共享存储，却要为每个 harness 单独集成，而且依赖模型主动调用。本文提出 **uni-mem**：一个运行在本机的单二进制 LLM 网关。所有 harness 只需把模型 API 的 base URL 指向它，就共享同一份按项目自动归档的长期记忆。uni-mem 有三个核心机制：(1) **overlay 重放**，网关对请求的每一处改动都以内容锚点记录，并在同一会话后续请求中逐字节重放，保证 prompt cache 前缀稳定；(2) **流式工具拦截与续写**，对 Anthropic Messages、OpenAI Responses、Chat Completions 三种方言，在网关内执行模型发出的 `unimem_*` 工具调用并续写上游生成，harness 只看到一条连续的回复；(3) 一个借鉴 Jev-Mem System-One/System-Two 划分的**记忆引擎**，用可插拔的类型化决策器处理"是否记、记到哪个作用域、是否覆盖旧记忆、是否相关、证据是否充分"等高频小判断。

所有评测都只用离线启发式决策器和哈希嵌入器，没有真实 LLM 参与，也没有真实 harness 流量。在样本外数据集 heldout2（242 条查询，233 条笔记，3 个 harness）上，v0.3 的 R@5 为 0.688，R@1 为 0.555，MRR 为 0.616，precision 为 0.423，过期笔记返回率为 16.3%。它在 R@5 上显著优于 v0.1（+0.119）、v0.2（+0.138）和 bm25-top5-cwd（+0.073），但**并未显著优于**使用同一嵌入器的 top-5 余弦检索（+0.018，95% CI [−0.037, +0.073]）。跨 harness 查询上，统一存储的 R@5 为 0.664，按 harness 隔离的 silo 为 0.000。网关流式路径的附加延迟为 p50 0.898 ms / p95 2.361 ms。30 轮对话中 42/42 次上游请求转换都是逐字节前缀扩展；1060/1060 条拦截正确性断言通过。主要负面结果是：写入端的安全筛查没有泛化（样本外提示注入仅拦截 1/7，状态笔记 1/6，而样本内均为 100%）；跨语言检索 R@5 只有 0.333；图扩展和被动门控没有可测量的贡献。

**关键词**：编码智能体；长期记忆；LLM 网关；prompt cache；工具拦截；System One

## 1 引言

### 1.1 问题

编码智能体正在成为开发者的日常工具，而且同一个人往往同时使用多个 harness。各 harness 都已有自己的记忆机制：

- **Claude Code** 提供 auto memory。记忆存放在 `~/.claude/projects/<project>/memory` 目录下，以 `MEMORY.md` 为索引；会话开始时加载索引的前 200 行或 25KB。此外还有 `CLAUDE.md` 形式的静态项目指令。
- **Codex CLI** 提供本地 memories（`~/.codex/memories`），由后台抽取与整合流程生成，默认关闭；静态指令则写在 `AGENTS.md`。
- 其它工具大多有各自的规则文件。

这些机制有三个共同问题。第一，它们是**孤岛**：用户在 Claude Code 里纠正过的一件事，Codex 不知道。第二，它们大多不区分"关于我"和"关于这个仓库"的记忆。第三，`CLAUDE.md` / `AGENTS.md` 是静态指令文件，需要人工维护，不是随交互积累的记忆。

一种自然的解法是把记忆做成 MCP server 或 hook，让多个 harness 共享。但 MCP/hook 体系在各 harness 之间并不兼容，每接入一个 harness 都要单独集成；而且 MCP 模式下记忆是否被使用，完全取决于模型是否主动调用工具，网关无法做被动召回。

### 1.2 思路

uni-mem 从一个观察出发：**每个 harness 都一定会调用模型 API，而且都允许修改 base URL**。模型 API 是唯一"零适配"的公共接入点。把记忆层放在这里，就能在不改动任何 harness 的前提下为它们提供共享记忆。这个位置也带来了新的工程约束：网关挂在所有流量前面，不能破坏 prompt cache，不能让 harness 看到它不认识的工具调用，任何异常都必须退化为透传。

### 1.3 贡献

1. 提出网关式统一记忆的架构，并给出一组从第一性原理推出的设计约束（§3.1）。
2. 设计了**缓存稳定的注入与 overlay 重放**机制：以 harness 原样回传的内容为锚点，并按会话与前一条消息隔离（§3.3）。
3. 设计了覆盖三种 API 方言的**流式工具拦截与续写**状态机，包括混合轮次（网关工具与 harness 工具同时出现）的处理（§3.4）。
4. 实现了一个 Rust 记忆引擎：四视图关系图、可插拔的 System-One 决策器（每个问题都带代码计算的先验）、自适应截断与充分性信号（§3.6），以及确定性硬信号加模型软信号的项目识别（§3.7）。
5. 给出一套刻意区分样本内/样本外的评测，并如实报告负面结果，包括 v0.2 "修复即过拟合"的教训（§5）。

## 2 相关工作

**Harness 内置记忆。** Claude Code 的 auto memory 与 `CLAUDE.md`、Codex 的 memories 与 `AGENTS.md`（见 §1.1）都绑定在单个 harness 的格式与目录中。uni-mem 不替代这些机制，而是在它们之外提供一个跨 harness 的共享层。

**MCP 记忆服务器。** jevmem、memsearch、mimir 等项目以 MCP server 形式提供记忆的存取工具。它们可以跨 harness 共享存储，但需要每个 harness 配置 MCP，并依赖模型主动调用。uni-mem 也提供 MCP 端点作为退路（§4），但主路径是网关：网关能看到全部对话，因此可以做被动召回、会话序言和对话流水捕获。

**Memory-first 代理。** BladeX 同样采用"在模型 API 前放一个记忆代理"的思路，是同期工作。uni-mem 是独立地从第一性原理设计的，二者在 overlay 重放、工具拦截续写、作用域判定等具体机制上可能存在差异；本文没有与 BladeX 做实验对比。

**Jev-Mem 与智能体记忆系统。** Jev-Mem（arXiv 2609.23986）提出把记忆系统中大量的类型化小决策交给快速、便宜、输出概率的 "System One" 模型，阈值写在代码里；环路中的大模型（"System Two"）负责撰写与推理。uni-mem 的记忆引擎直接沿用了这一划分。Jev-Mem 文中讨论的 MAGMA、A-MEM、MemoryOS、Nemori 等系统，在记忆组织（图结构、多视图、分层与整合）方面也影响了本文的数据模型设计；本文没有复现这些系统，也没有与之进行数值比较。

## 3 设计

### 3.1 第一性原理

设计文档（`docs/DESIGN.md` §0）列出了七条约束：

1. **记忆属于人，不属于工具。** 记忆层必须位于所有 harness 之外，由它们共用。
2. **唯一普适的接入点是模型 API。** 网关是唯一零适配的位置。
3. **网关在本机，因此能看到文件系统。** 项目识别的硬信号（git root、remote、manifest）可以确定性地获得，只有语义部分需要模型判断。
4. **环路里已经有最聪明的模型（System Two）。** 它是最好的记忆撰写者，不必再额外请一个大模型做总结，只需给它工具。
5. **高频小决策交给 System One。** 阈值写在代码和配置里，决策可追踪。
6. **不能让用户为记忆付出缓存代价。** 任何注入要么在整个会话内逐字节稳定，要么位于尾部并在之后原样重放。
7. **失败必须透明。** 记忆层任何异常都退化为纯透传。

### 3.2 总体架构与 Turn 分类

uni-mem 监听 `127.0.0.1:4777`，暴露 `/v1/messages`（Anthropic）、`/v1/responses`（OpenAI Responses，Codex 使用）、`/v1/chat/completions` 与 `/mcp`。请求依次经过方言适配、Turn 分类、上下文提取（cwd、会话）、overlay 重放、工具注入与项目解析，然后转发上游；响应经流式改写器返回。上游鉴权头（API key 与订阅 OAuth）原样透传。

harness 会发出大量辅助请求，例如标题生成、bash 前缀判定、压缩摘要、quota 探测，这些请求不应注入记忆。分类规则是：

- 请求带 `tools` → **agent turn**：注入工具，执行 overlay 重放；
- 最后一条消息是用户新输入（不是纯 tool_result）→ **prompt turn**：额外执行被动召回；
- `count_tokens`、无工具请求、模型列表等 → 纯透传（`count_tokens` 会附加工具定义，以便 harness 的上下文估算包含它们）。

### 3.3 缓存稳定的注入与 overlay 重放

Anthropic 与 OpenAI 的 prompt cache 都按前缀匹配。网关对请求的任何非稳定修改都会使后续缓存失效。uni-mem 的注入位置因此严格受限：

| 注入内容 | 位置 | 稳定性 |
|---|---|---|
| 工具定义 | 追加到 `tools` 数组末尾 | 内容固定，逐字节稳定 |
| system prompt | **不修改** | 部分订阅鉴权会校验 system 前缀 |
| 会话序言（项目卡片 + 置顶记忆） | 第一条 user 消息末尾 | 会话内冻结 |
| 被动召回 | 当前 user 消息末尾（请求尾部） | 之后由 overlay 重放 |

每一处修改都记录为 overlay。overlay 有两类：

- **`augment_user`**：锚点为 `aug_anchor(session, key(前一条消息), key(本消息))`，载荷是追加到该 user 消息后的 `<unimem…>` 文本。空文本表示"已处理、无需追加"，这样同一个 prompt 的重试是幂等的。
- **`expand_assistant`**：锚点为 `exp_anchor(session, key(前一条消息), hash("vis", visible_key(msg)))`。harness 看到的是合并后的一条 assistant 消息，重放时把它整体替换为上游真实产生的序列：`assistant(含 unimem tool_use) → user(tool_result) → assistant(续写)`。混合轮次中，网关的 tool_result 被前插到下一条 user 消息。

`visible_key` 只取 `text` 块的去空白文本与 `tool_use` 的 id，忽略 thinking、签名、citation 和 cache_control，所以从网关流出的内容与 harness 回传的内容能算出相同的 key。找不到锚点时（历史被压缩或编辑）直接跳过，请求仍然合法，只损失这部分上下文。

**会话隔离。** v0.1 的展开锚点只用 `hash(前一条消息 key, 可见 key)`，并以 `ON CONFLICT DO NOTHING` 写入。评测中的锚点碰撞探针发现：两个会话发送相同 prompt 并得到相同可见回复时，第二个会话的下一次请求会被重放第一个会话的隐藏工具调用与结果（10/10）。v0.2 把会话 key 纳入锚点，问题消失（0/10，§5.5）。

### 3.4 流式工具拦截与续写

网关向模型暴露 `unimem_recall`、`unimem_remember`、`unimem_forget`、`unimem_project` 四个工具。harness 不认识它们，所以这些调用绝不能流到 harness。流式改写器是一个状态机：

1. 边读上游 SSE 边转发，维护 block/item 索引映射；
2. 遇到 `unimem_*` 的 tool_use 块时缓冲而不转发，并重新编号后续块的索引；
3. 上游以 `stop_reason=tool_use` 结束时：
   - **只有网关工具**：吞掉 `message_delta/message_stop`，在网关内执行工具，把 `assistant + tool_result` 拼进请求后再请求上游；跳过新流的 `message_start`，按索引偏移接到原流后面。最多续写 `max_continuations` 轮（默认 6）。
   - **混合轮次**：harness 自己的工具调用照常交给 harness；网关工具在网关内执行，结果存入 overlay，下一次请求时补回。
4. usage 在多轮之间累加，最终的 `message_delta` 给出合并值。

三种方言共享同一套架构，只是粒度不同：

| 方言 | 单元 | 拦截与重放要点 |
|---|---|---|
| Anthropic Messages | content block | 块索引连续重编号；`expand_assistant` 整体替换可见 assistant 消息，保留 thinking 块与其后的工具调用的对应关系 |
| OpenAI Responses | output item | `output_index` 与 `sequence_number` 重编号；最终 `response.completed` 的 `output` 只含可见 item；隐藏 item 以相邻可见 item（call_id、reasoning 的 `encrypted_content` 哈希、消息文本哈希）为锚点插回；`instructions` 不修改 |
| Chat Completions | message / `tool_calls[].index` | 网关的 `tool_calls` 被隐藏，其余调用连续重编号；后续轮次文本以空行接续；`n > 1` 的请求直接透传 |

### 3.5 失败策略

- 召回超时（`recall_budget_ms`，默认配置 1500 ms）→ 不注入，直接透传；
- 改写阶段出错 → 退回原始请求；
- 工具执行出错 → 错误作为 tool_result 交给模型自行处理；
- 上游错误 → 状态码与 body 原样返回。

### 3.6 记忆引擎

**数据模型。** `Memory` 包含作用域（`global` 或 `project:<pid>`）、类型（fact / decision / preference / procedure / gotcha / episode）、内容、可选的 `why`、实体、来源（harness、会话、cwd、git 分支与提交）、`superseded_by`、显著度、命中次数、置顶标记与嵌入向量。`Edge` 的关系类型有 semantic、temporal、causal、entity、supersedes、duplicate。此外还有 `Project`、`Episode`（无损对话流水，是被动蒸馏的原料）与 `Overlay`。全部存放在单个 SQLite 文件中。

**四视图关系图。** 语义、时间、因果、实体四类边构成同一张记忆图的四个视图，另有 supersedes 与 duplicate 两类维护边。代码负责确定性边（如同会话的时间序），其余边由 System One 的概率判断超过阈值后建立。

**可插拔 System One。** 决策器接口接收一个状态和一批类型化问题（是非题 `Noul`、选择题 `Choice`），返回带概率的答案。**每个问题都携带由确定性代码计算的先验**（相似度、正则、关键词、校准过的逻辑回归）。后端有四种：

- `JevDecider`：TypeSafe `/v1/systemone` 或兼容服务；
- `LlmDecider`：任意 OpenAI 兼容小模型，以 JSON 输出模拟类型化问题；
- `HeuristicDecider`：离线、确定性，直接返回先验；
- `ChainDecider`：按顺序尝试，前一个不可用就降级。

因此系统在完全没有模型时也能工作，阈值（如 `T_INJECTION=0.6`、`T_DUP=0.8`、`T_SUPERSEDE=0.7`、`T_GLOBAL_PREF=0.6`）写在代码中，并注明"为启发式先验标定，换决策模型需重新标定"。

**写路径。**

1. 代码筛查：过短（<8 字符）、过长（>2400 字符）、密钥（厂商格式与"关键词 + 值"两类正则）直接拒绝；
2. 一次批量 System-One 调用，问题包括 `durable`（是否持久事实而非"下一步做 X"）、`injection`（是否针对 agent 的提示注入）、`kind`、`scope`（在 global / 当前项目 / 文中提到的其它已知项目之间选择，**由模型决定写全局还是写项目**）；
3. 在相关作用域内取候选邻居，嵌入余弦 ≥ 0.97 且主题一致时直接判为重复；
4. 对候选做批量关系判断：duplicate、supersedes、explains_why（因果）、same_entity。v0.3 的 supersede 与 duplicate 都加入了**主题（subject）检查**：只有同类型、同作用域、主题最接近的候选才可能被替换；
5. 写入节点、边、FTS 与向量。被 supersede 的旧记忆只降权，不删除。

**读路径。**

1. **Gate**（仅被动召回）：短确认语或信息量过少的输入直接跳过；
2. **Anchor**：词法检索（BM25，k1=1.2、b=0.75，基于词干、CJK 单字与双语概念词）加向量检索，范围是当前项目 + global，提问中提到其它项目名或别名时也加入该项目。v0.1 用 RRF 融合；v0.3 改为**校准的逻辑回归先验**，特征包括 idf 加权覆盖率、相对 BM25、余弦及其相对值、"问为什么且笔记给出理由"；
3. **Score**：对前 14 个候选批量询问相关性；
4. **Expand**（多跳查询）：只沿因果边和（涉及时间变化时）时间/supersedes 边从高置信锚点展开，不展开语义/实体邻居；
5. **自适应截断**：笔记相关性需不低于 `T_RELEVANT=0.12`，且不低于最佳笔记的 `KEEP_RATIO=0.4` 倍。agent 主动召回时，若无笔记过线，返回一个不低于 `T_WEAK=0.06` 的最佳弱候选（并标记为不充分）；
6. **过期值安全网**：同一主题、取值不同的候选中保留最新者，其余降权并标记；
7. **Sufficiency**：以最佳候选的校准概率构造先验（0.5 对应 `T_SUFFICIENT=0.3`），返回 `sufficient/missing` 信号，让 agent 知道"我不知道"。

### 3.7 项目识别

- **硬信号（确定性）**：cwd → git root（处理 worktree 的 `.git` 文件、`gitdir:` 与 `commondir`）→ remote → manifest（Cargo.toml / package.json / pyproject）→ README 首段。`pid` 优先取规范化的 `host/owner/repo`，同一仓库的所有 clone 与 worktree 共享一个项目；无 remote 时取 git root，再否则取 cwd。v0.2 加入了 manifest 向上查找与路径规范化（符号链接）。
- **软信号（模型）**：项目卡片的 `summary` 先由 README/manifest 生成启发式初稿，环路中的 agent 可随时用 `unimem_project` 改写，这比网关自己再调一次模型更准、更便宜；写入作用域由 System One 判定（§3.6）；跨项目引用通过检测提问中的项目名与别名实现。

### 3.8 被动捕获

每个 prompt turn 的用户输入与 assistant 文本都写入 `episodes`。会话空闲后，可选的蒸馏器从流水中抽取用户纠正、明确偏好、带理由的决定与陷阱，再走标准写路径。蒸馏器默认关闭；默认只开启 agent 显式写入。本文没有评测蒸馏器。

## 4 实现

uni-mem 是一个 Rust（edition 2021）单 crate 项目，产出两个二进制：`unimem`（网关与 CLI）和 `unimem-bench`（评测）。主要依赖为 axum 0.8、tokio、reqwest（rustls）、rusqlite 0.37（bundled SQLite，含 FTS5）。代码规模（`wc -l`，HEAD `9dcc43a`）如下：

| 部分 | 行数 |
|---|---|
| 库与主程序 `src/`（不含 bench） | 8,235 |
| 评测程序 `src/bin/unimem-bench.rs` | 2,075 |
| 集成测试 `tests/` | 2,015 |
| 合计 | 12,325 |

### 5.5 版本演进与 v0.2 的教训

### 5.6 E2：网关开销、缓存稳定性与拦截正确性

E2 使用模拟上游（立即响应，设置 TCP_NODELAY），每个单元 300 次请求，请求体约 31.5 KB（仿 Claude Code：12 个工具、约 11 KB system prompt）。表中数字是网关本身的开销。

**表 7** 相对直连的附加延迟（逐请求配对差值，ms）

| 路径 | v0.1 ΔTTFB p50 / p95 | v0.2 ΔTTFB p50 / p95 | **v0.3 ΔTTFB p50 / p95** |
|---|---|---|---|
| gateway/stream（即 `unimem serve`） | 42.807 / 48.580 | 0.754 / 1.046 | **0.898 / 2.361** |
| gateway/json | 0.477 / 0.663 | 0.217 / 0.279 | 0.219 / 0.289 |
| gateway-norecall/stream | 1.019 / 47.721 | 0.220 / 0.311 | 0.226 / 0.337 |
| gateway-nodelay/stream | 2.038 / 3.418 | 0.765 / 1.040 | 0.894 / 2.457 |

**TCP_NODELAY 的发现。** v0.1 的 `unimem serve` 没有在客户端 socket 上设置 `TCP_NODELAY`。SSE 写出大量小块，在 Linux 回环上触发 Nagle 与 delayed-ACK 的交互，流式路径因此增加约 43 ms TTFB；同一状态下由 bench 强制 NODELAY 时只增加约 2 ms。v0.2 在监听器上为每个接受的连接设置 NODELAY（`nodelay_listener`），之后 `gateway/stream` 与 `gateway-nodelay/stream` 一致。v0.3 的流式召回开销（p95 2.4 ms）高于 v0.2（1.0 ms），与 v0.3 更昂贵的召回路径相符，但未单独 profile。另外，v0.2 二进制的直连路径绝对值约快 2 倍（direct/json TTFB p50 0.136 ms 对 0.245–0.257 ms），原因未查明，因此只比较附加延迟。

**表 8** prompt cache 稳定性（30 轮流式对话，v0.3）

| 模式 | 上游请求 / 续写轮 | 平均前缀比例 | 最小 | 完全稳定转换 | 可缓存字节比 | 上游字节 |
|---|---|---|---|---|---|---|
| Passthrough | 37 / 0 | 1.000 | 1.000 | 36/36 | 0.987 | 1,533,573 |

| NaiveTail（尾部注入不重放） | 37 / 0 | 0.991 | 0.969 | 7/36 | 0.979 | 1,546,544 |

uni-mem 的每一次上游请求都是上一次的逐字节前缀扩展，与纯透传相同；把召回写入 system prompt 只有 9/36 次转换完全稳定，尾部注入而不重放只有 7/36。代价是上游字节数增加：6 次额外的全上下文续写请求使总字节增加 60%（v0.2 为 +71%）。这些字节绝大部分是可缓存前缀，但请求次数和未命中缓存的输入 token 仍会增加。

**拦截正确性。** 脚本化轮次覆盖仅召回、仅写入、混合（unimem + Bash）、仅 Bash 和纯文本，流式与 JSON 各一套，每轮带一个回传可见消息的后续请求。120 次客户端请求对应 144 次上游请求（24 轮续写），**1060/1060 条断言通过**（三个版本都是）。断言族包括：客户端从不看到 unimem 工具或上下文、SSE 帧合法、system 未改动、工具按序追加、隐藏轮次逐字节重放、混合轮次的隐藏调用与结果被重放、可见 stop reason 正确等，全部 100%。**锚点碰撞探针**：两个会话发送相同 prompt 并得到相同回复时，第二个会话被注入第一个会话隐藏轮次的次数为 v0.1 10/10、v0.2 0/10、v0.3 0/10。

### 5.7 E3：项目识别

37 种合成目录布局，覆盖各类 remote 格式（scp/ssh/https/git、含 token、大写、尾斜杠、非标准端口）、worktree（含相对 gitdir + commondir）、submodule、嵌套仓库、fork、GHE 与 GitLab 子组、无 remote 仓库、非 git 的 manifest 目录、dotfiles 仓库作为 home、符号链接，以及"首次见到后才加 remote 时身份保持"。结果为 v0.1 35/37，v0.2 与 v0.3 均为 37/37；v0.2 修复的正是 v0.1 报告的两例（非 git manifest 目录的子目录；指向无 remote 仓库的符号链接）。没有样本外布局，因此这是样本内结果。

## 6 讨论与局限

本文的结论必须放在以下限制下理解：

1. **没有真实模型参与。** 所有 System-One 判断都是启发式决策器返回的代码先验，嵌入器只有离线哈希嵌入。Jev 或 LLM 决策器、语义嵌入模型可能大幅改变筛查、去重/覆盖、作用域和相关性的数字，方向未知。代码中的阈值也明确标注为"为启发式先验标定"。
2. **没有真实 harness 流量。** E2 使用模拟上游和脚本化的仿 Claude Code 请求。网关在真实 Claude Code / Codex 各版本下的回传格式（尤其是 thinking 块被裁剪、历史被压缩的情况）尚未用真实流量回归。Codex 使用 ChatGPT 登录时的自定义 provider 鉴权透传尚未在真机验证。改写订阅流量是否符合服务商条款，需要用户自行确认。
3. **数据集是合成的。** 三个数据集都由 LLM 智能体编写，规模为两百条量级，单一用户画像，与真实开发者的记忆分布可能差异很大。heldout2 存在 `queue`/`retry` 两条双语提示的潜在词汇泄漏。
4. **安全筛查没有泛化。** 样本外注入拦截 1/7、状态笔记 1/6，被存下来的注入随后被当作答案返回（n174）。这是安全问题而不仅是质量问题，也说明正则加关键词先验无法应对开放世界的注入表述。
5. **跨语言检索薄弱。** heldout2 上跨语言可回答查询（48 条）的 R@5 为 0.333，同语言（170 条）为 0.788；bm25-cwd 与 vector-cwd 也有同样落差（0.250/0.718、0.333/0.765），是所有词法/哈希系统共有的弱点。64 条双语提示表只覆盖通用开发词汇。
6. **R@5 不显著优于同嵌入器的余弦检索。** uni-mem 的优势在于 R@1、MRR、precision 和过期规避，而不是召回覆盖。
7. **图扩展与被动门控没有可测量的贡献**（full = lite = passive）。四视图图结构目前更多是架构上的预留，尚无实证支持。
8. **充分性信号偏弱。** 可回答查询上 `sufficient=false` 仍有 45.0% 的误报；不可回答查询上"弃答或 sufficient=false"为 70.0%。它带有一些信息，但不足以据此行动。
9. **成本。** 写入延迟约为 v0.1 的 2.3 倍；流式召回网关开销 p95 2.4 ms；每条笔记存储比 v0.2 增加约 47%；续写使上游字节增加约 60%；召回仍是线性暴力检索。
10. **没有端到端任务指标。** 本文只度量检索与网关机制，没有度量记忆是否真正提升了智能体的任务成功率。蒸馏器也未评测。

## 7 未来工作

- **真实决策器的标定**：接入 Jev 与小型 LLM 决策器，在样本外数据上重新标定阈值，并比较与启发式先验的差距。
- **多语言嵌入**：用 bge-m3 等多语言嵌入模型（已支持 OpenAI 兼容 `/v1/embeddings` 接口）解决跨语言检索与跨语言去重。
- **真实流量回放测试**：录制 Claude Code、Codex 各版本的真实请求，回归 overlay 锚点的容错与 ChatGPT 登录鉴权透传。
- **注入分类器**：用专门训练的分类器或模型判断替代正则先验，并在独立的对抗样本集上评测。
- **ANN 索引**：引入近似最近邻或带作用域预过滤的索引，消除线性增长。
- **蒸馏评测**：度量被动蒸馏抽取的记忆的精确率与召回率。
- **端到端指标**：在真实编码任务上度量有/无统一记忆时智能体的成功率、重复纠正次数与 token 成本。

---

## 8 结论

uni-mem 表明，把长期记忆放在模型 API 网关这一层，可以在不改动任何 harness 的前提下，为异构编码智能体提供共享的、按项目归档的记忆，同时不破坏 prompt cache（42/42 次逐字节前缀扩展），也不向 harness 泄漏它不认识的工具调用（1060/1060 断言通过），流式附加延迟在毫秒以内（p50 0.898 ms）。在样本外数据上，v0.3 引擎在 R@1、MRR、precision 和过期规避上优于所有基线，并显著优于早期版本与 BM25 基线；但它的 R@5 并不显著优于同嵌入器的朴素余弦检索。写入端安全筛查没有泛化、跨语言检索薄弱、图扩展无可测贡献，这些是当前最主要的开放问题。所有结论都基于离线启发式决策器和合成数据。v0.2 的经验也说明，针对已知失败做的启发式修复很容易过拟合，样本外纪律对这类系统是必要的。
